# v7系の確認と移行

v7.1の日常操作は [日常の進め方](DAILY_WORKFLOW.md) を参照する。既存の承認は保持し、手書き資料の自動移行・再承認は行わない。

## 本人に確認してほしいこと

G1: 課題・採点条件・表紙・実験条件を確認する。確認票には基準の内容、合格条件、出典位置、推奨計画、詳細を読む場所を載せる。

G2: 実施事実、失敗・除外、主要結果、骨格PDF、文章枠の執筆要件を確認する。機械は実験した本人かどうかを判定しない。

G3: 本人には日本語の変更説明 `quality/PROSE_CHANGES.md` と最終PDFを示し、意図の一致・見た目・評価上の不足を確認してもらう。数値・単位・否定・因果・結論・断定強度の照合はCodexが先に行い、判断が必要な変更だけ質問する。詳細は `quality/PROSE_DIFF.md` に残す。機械検査だけで意味保存を保証しない。

## 部分執筆と本文レビュー

原文を無改変保存してから組版する。通常はCodexが次を実行する。

```powershell
python scripts/review_prose.py experiments/<id>
python scripts/review_prose.py experiments/<id> --slot P-001 --note "誤字と組版のみ。否定・因果・結論・数値・単位を照合した。"
python scripts/build_report.py experiments/<id> --mode draft
```

`--slot` は実際に読み比べた後だけ使う。数値・単位が変化すると通常レビューは拒否される。単位変換や参照組版による自動検出の誤警告も理由を説明し、必要なら本人確認を受ける。

意味変更が必要な場合は差分と理由を本人へ示す。実際の回答を次の形式で記録する。

```powershell
python scripts/review_prose.py experiments/<id> --slot P-001 --note "変更の理由" --decision "承認 P-001: 承認した具体的な変更"
```

Codexはこの承認を捏造しない。原文・組版後のどちらかを変更したら、対象枠だけ再レビューする。未入力枠を残した下書きは作れるが、未確認の組版ファイルは削除・退避してから下書きにする。完成候補には全枠完成が必要である。
レビュー処理は記録済み原文の改変を新しい原文として再封印しない。本人が新しい原文を送った場合は `receive_prose.py` を使って旧版と受領元を保存し、改めて対象枠をレビューする。

## PDFと確認記録

`build_report.py` が `quality/SKELETON_BUILD.yaml`、`DRAFT_BUILD.yaml`、`CANDIDATE_BUILD.yaml` を自動生成する。入力の一覧・照合値・PDF照合値を保存する。TeX recorderで読まれた実験内の追加ファイルも対象にする。共通クラスや様式契約の変更も旧PDFを失効させる。

最終候補を全ページ画像で確認し、現在の候補に対して技術・内容・教授視点レビューを行い、その内容を記録した後に実行する。

```powershell
python scripts/workflow.py bind-reviews experiments/<id>
python scripts/workflow.py prepare-review experiments/<id> --gate G3
```

`bind-reviews` は対象版を記録するだけで、評価・目視を実施せず、passedへ変更もしない。新しい候補を確認する前に実行してはいけない。同一入力・同一PDFを再生成しただけなら確認記録を再利用できる。内容またはPDFが違えば確認をやり直す。

骨格PDFは全文章枠を含む版としてG2で固定する。本文を埋めてもG2の骨格確認は有効だが、見出し・図表・枠の要件を変えると再承認が必要になる。
例外は `LAYOUT_TUNING.yaml` の限定的な図幅・フロート間隔だけである。これは骨格へ適用せず候補へだけ適用し、候補の版とG3に接続する。任意のTeX差分を意味不変と見なす仕組みではない。
架空例の骨格は `examples/sort-benchmark/preview/skeleton.pdf` にも保存する。完成後のクリーン取得でbuildがない場合、G2は保存された生成記録と現在の入力を照合し、previewがあればPDFも照合する。実験の骨格を再び目視したい場合は再生成する。

## 教授視点評価

まず実習書・G1の基準・現在の候補・証拠を読み、不足と減点要因を列挙する。過去の自己採点を引き継がない。判定、本文位置、具体的証拠、厳しい指摘、改善案、判断不能事項を記録する。

教員提供の全項目で正の `max_score` と `weight` が明示されている場合だけ、各得点と加重百分率を計算する。内部基準・尺度不明・配点不明なら得点と総合点は `null` にし、定性的に評価する。点数は実際の成績予測ではない。

## 承認・提出保存

G1は事前契約、G2は実施事実と骨格、G3は完成稿と理解確認を扱う。後日の理解確認を更新してもG1は失効しない。計画変更は後続承認にも影響する。再確認票には変更対象を載せ、会話では変更の影響を優先する。

提出版は検査済みの一式を一時領域へ揃えてから置換する。固定後検査に失敗すると直前版へ復元する。成功後も直前版は `build/release-backups/` に残る。バックアップはGit管理されないため、必要なら本人が別途保管する。

## v6以前からの移行

### v7.2の学習範囲

新規の `workflow/STATE.yaml` はversion 2であり、`task_scopes` がないとPHASE 1で停止する。version 1で範囲が未設定の既存実験・完成例は従来検査を維持するが「学習範囲監査は未適用」と表示する。旧例の承認を勝手に上書きしない。

既存実験で学習範囲監査を始める場合、Codexが要件に課題別範囲を追加し、文章枠のtask_ids、骨格・教授評価のtask_scope_reviewsを記入する。STATE.versionを2に更新し、G1から変更の影響を確認して必要な本人承認を取り直す。範囲設定はG1、文章枠と骨格範囲レビュー・宣言したコードはG2、最終範囲レビューはG3に接続される。版の更新自体は本人承認の代わりではない。

### v6以前の追加対応

1. 元の実験と提出PDFを保管する。
2. 新しいコードでG1確認票を準備し、必要な再承認を本人に求める。G1時点で未実施の確認は未確認のままでよい。
3. 再現性検査を行い、骨格を再生成してG2を再確認する。
4. 受領原文を変更せず、各組版枠を読み比べて版付きレビューを記録する。
5. 候補を再生成し、全ページ・内容・教授視点を再確認する。旧点数は配点がないなら廃止する。
6. `bind-reviews`、G3確認・本人承認、releaseへ進む。

既存実験の本人承認をAIが自動移行しない。`--migration-example` はリポジトリの架空例専用であり、本人の実レポートに使えない。

## 検査できる範囲

Pythonは版、構造、数値・単位トークン、再生成、PDF技術条件を検査する。任意のTeXマクロを解釈する検査器ではない。複雑な条件分岐や動的入力は使わず、literalなinput/includeを使う。意味、出典本文との一致、実施事実、採点上の妥当性、図表の見やすさはCodexと本人の確認が必要である。
