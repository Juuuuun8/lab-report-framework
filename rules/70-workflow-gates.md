# 3つの本人承認ゲートとPHASE 0〜8

PHASE 0〜8はCodexが内部品質を落とさないための検査段階であり、ユーザーが9回承認する仕組みではない。ユーザーの判断は、次の3回へ集約する。

| 承認 | 内部Phase | ユーザーが判断する内容 | 承認前に禁止すること |
|---|---|---|---|
| G1 実験契約 | 0〜2 | 課題解釈、提出条件、表紙、AI利用、実験計画 | 実験の開始 |
| G2 証拠と論証方針 | 3〜5 | 実施事実、生データ、除外・逸脱、主要結果、考察方針 | 本文執筆 |
| G3 提出 | 6〜8 | 個人情報、最終候補PDF、説明可能性、提出可否 | `deliverables/report.pdf` への昇格 |

`workflow/G1_REVIEW.md` などの確認票は最大5項目の要約と、ユーザーにしか確認できない事項を示す。正常な検査ログをユーザーへ読ませない。承認時には対象ファイル一覧のSHA-256集合ダイジェストを `workflow/STATE.yaml` に固定する。承認対象の実質的内容が変われば承認は失効し、再確認が必要になる。OS間で意味のない改行コード差だけは正規化する。

途中で新しい不確実性が生じた場合は、採点、実験条件、データ除外、再実験、安全、期限、費用、AI規則、結論に影響するときだけ相談する。それ以外はCodexが規則に従って処理し、次の承認票へ差分としてまとめる。

標準操作は次のとおりである。

```text
準備 → G1確認・本人承認 → 実験・分析・出典検証
     → G2確認・本人承認 → 執筆・推敲・PDF監査
     → G3確認・本人承認 → 提出物へ固定
```

## PHASE 0: 受領・保全

作業:

- 実習書、課題文、配布コード、データ、提出要件を収集する。
- ファイル一覧、形式、ページ数、ハッシュ、判読可否を記録する。
- 元ファイルを変更せず保全する。

ゲート:

- `instructions/INPUT_INVENTORY.md` が存在する。
- 実習書・課題文の欠落や判読不能ページが明示されている。
- 対象実験と提出期限が分かるか、未決として質問に上がっている。

## PHASE 1: 要求理解・事前質問

作業:

- 実習書を最初から最後まで読む。
- 提出形式、必須章、課題、評価観点、禁止事項を抽出する。
- `ASSIGNMENT_REQUIREMENTS.yaml` に実習書の参照位置付きで要求と採点基準を記録する。
- `ACADEMIC_INTEGRITY.yaml` でAI利用可否、開示要否、本人実施範囲を確認する。
- 表紙項目、実験条件、利用可能環境、提出物、相談が必要な判断を `QUESTIONS.md` にまとめ、可能な限り最初に一括して尋ねる。
- 回答を `spec/USER_DECISIONS.yaml` に保存する。

ゲート:

- `instructions_read_complete: true`。
- 必須質問がすべて `resolved` または、ユーザーが明示的に Codex へ判断を委任している。
- 表紙項目が `REPORT_META.yaml` に反映されている。
- 根拠のない仮定がない。
- AI利用規則が `unknown` のままではない。

## PHASE 2: 実験計画

作業:

- 目的、仮説または確認事項、変数、統制条件、試行回数、順序、停止条件、除外基準、分析方法を定める。
- 必要な計測精度、ログ、ファイル名規則、リスクを定める。
- ユーザー承認が必要な選択肢を相談する。

ゲート:

- `spec/EXPERIMENT_PLAN.yaml` が完成している。
- 結果を恣意的に選ばない事前規則がある。
- 実行可能性と安全性を確認済みである。

## PHASE 3: 実験実行

作業:

- 計画どおり実行し、日時・環境・版・条件・観察を記録する。
- 生データを `data/raw/` に不変保存する。
- 失敗、再試行、計画逸脱を記録する。
- `EXECUTION_MANIFEST.yaml` に環境、実行単位、各生データファイル、失敗・除外・逸脱を記録する。

ゲート:

- 生データと実行ログが存在する。
- 各試行の条件を復元できる。
- 逸脱とデータ除外が明示されている。

## PHASE 4: 分析

作業:

- スクリプトでデータを処理し、処理済みデータ、統計量、図表を生成する。
- 有効数字、単位、異常値処理を確認する。
- 想定外の結果を隠さず、必要ならユーザーへ再実験を相談する。

ゲート:

- 同じ入力と環境で主要結果を再生成できる。
- `RESULT_TRACEABILITY.md` の主要結果行が埋まっている。
- 表・図・本文候補の数値が一致する。

## PHASE 5: 出典検証

作業:

- 外部知識が必要な主張を列挙する。
- `CLAIMS.yaml` に外部主張、結果、推論、限界、方法を列挙し、Source IDとResult IDへ接続する。
- 優先順位に従い資料を探し、本文を開いて該当箇所を確認する。
- `spec/SOURCES.yaml` と `SOURCE_AUDIT.md` を更新する。

ゲート:

- 本文中の全外部主張に verified な出典がある。
- locator と内容一致メモがある。
- 日本語一次・公式情報を優先できなかった場合は探索記録がある。
- URLとアクセス日を確認済みである。

## PHASE 6: 執筆・TeX

作業:

- 実習書指定の構成で執筆する。
- 図表、式、コード、引用を共通規則に従って配置する。
- `HANDOFF.md` を含む補助成果物を更新する。
- 採点項目を `RUBRIC_TRACEABILITY.md` で本文位置と証拠へ対応させる。
- 共通様式の変更は本文へ直接書かず、根拠と承認を `STYLE_OVERRIDES.yaml` に記録する。

ゲート:

- 未解決のプレースホルダがない。
- 図表は本文で先に参照され、番号・キャプション・本文説明がある。
- 表紙後にタイトル・氏名・概要・キーワードを再掲していない。
- TeX が警告を含め監査され、PDFを生成できる。

## PHASE 7: 日本語推敲・Codex再監査

作業:

- Antigravity が `ANTIGRAVITY.md` の範囲だけで推敲する。
- 推敲前に `polish_guard.py snapshot`、推敲後に `polish_guard.py verify` を実行する。
- Codex が差分を再監査する。

ゲート:

- 数値、単位、式、図表、引用、断定の強さが意図せず変わっていない。
- 文体、用語、句読点が統一されている。
- 再監査結果が `WORKLOG.md` にある。

## PHASE 8: 提出物固定

作業:

- PDFを全ページ画像化して、欠け、重なり、空白、図表の可読性、改ページを目視確認する。
- 自動検査と最終チェックリストを実行する。
- 提出物を `deliverables/` に集約する。

ゲート:

- `report.pdf`、`HANDOFF.md`、`SOURCE_AUDIT.md`、`RESULT_TRACEABILITY.md`、`WORKLOG.md` が存在する。
- `RUBRIC_TRACEABILITY.md`、`ORAL_DEFENSE.md`、`QUALITY_REVIEW.yaml` が存在する。
- 必須採点項目と8つの内容品質検査が合格している。
- PDFのページ数、用紙サイズ、埋め込みフォント、リンク、本文抽出を確認済みである。
- 視覚欠陥がない。
- `python scripts/validate_experiment.py <path> --phase 8` が成功する。
