# 数式・コード

## 数式

- 文中の数式も文の一部として扱い、必要に応じて句読点を付ける。
- 本文から参照する式だけに通し番号を付け、右端へ配置する。
- 本文では「式 (1)」のように参照し、式より前または直後に全ての記号を定義する。
- 変数は斜体、演算子・単位・関数名は立体とする。
- 単位は数値と分離し、SI単位系を基本とする。例: `10.0 ms`。
- 導出が長く本文の論理を妨げる場合は付録へ移す。
- 計算結果は元データ、式、スクリプトのいずれかへ追跡可能にする。

## コード

- 本文には議論に必要な最小部分だけを掲載する。
- 通し番号と日本語キャプションを付け、本文で先に参照する。キャプションはコードを読む前に内容を把握できるよう、リストの上に置く。
- 等幅書体、行番号、自然な折り返しを使い、装飾の強い枠や背景を避ける。
- 長いプログラム、生成コード、依存ライブラリの全文は付録または別ファイルにする。
- 省略箇所がある場合は明示し、実行可能な完全版のパスまたはコミットを示す。
- 端末入出力は画像ではなくテキストとして掲載する。必要ならプロンプトと出力を区別する。
- APIキー、個人情報、認証情報、絶対パスを掲載しない。

## 課題の到達段階に合わせる

- 実装前に対象TASKと `task_scopes` を読む。実習書全体は規則確認のため全読するが、解法・分析・図表・見出し・執筆案内には当該課題までの範囲と確認済みの既習事項だけを使う。
- 後の課題の解法、実験結果、考察の結論を前の課題に既知として持ち込まない。外部資料もこの境界に従う。前提課題は先に記録されたTASKに限る。
- 使用言語、アルゴリズム、関数名・引数、入出力、変更禁止箇所、許可ライブラリなどの指定は `requirements` に出典位置付きで記し、TASKから参照する。
- 自作が目的の処理を組み込み関数や外部ライブラリで置き換えない。実習書にない技法でも既習・許可済みなら使えるが、不明で結果に影響する場合だけ確認する。
- 正確で見通しのよい実装を選ぶ。必要のないクラス化、設計パターン、互換処理、汎用化、高度な最適化を追加しない。学生らしさを演出するために誤りを入れたり、品質を落としたりしない。
- 提出コードと検算・集計・組版などの補助コードを別ファイルとして指定する。同じものを両役割に登録しない。補助コードも授業の禁止・利用制限を守り、課題の核心を迂回して解かない。
- コメントは指定言語・様式を優先する。指定がなければ日本語を基本とし、目的、理由、前提、境界条件を必要な箇所に簡潔に記す。コードの逐語訳、過剰な章立て、実施していない苦労・試行錯誤・観察の記述は避ける。
- G2で `WRITING_PLAN.yaml.task_scope_reviews` に対象箇所と判断根拠を記録する。G3で教授視点の `task_scope_reviews` に本文を含む完成稿の確認を記録する。変更のないコードの説明を再作文せず、既存の箇所を参照してよい。
- Pythonは範囲の宣言・対応・記録・ファイルの版を検査する。先取りやコメントの適切さをコード解析で自動判定するものではない。
